# Multi-Tag Query Decomposition Implementation Plan

> **For Hermes:** Execute this specification only after approval, reconciling the currently uncommitted prototype against the contract below.

**Goal:** Detect when an MCP caller has concatenated multiple known tags into one `search_knowledge` query, resolve each tag independently, and return explicit guidance for the agent to search the parts separately.

**Architecture:** Keep the existing exact → normalized → B-tree prefix → FTS5 → fuzzy precedence for a complete query. Add a deterministic decomposition step only after the complete query has no results. The decomposition must prefer known multi-word tags and preserve contextual character/franchise queries before considering independent tag parts.

**Tech Stack:** Python 3.11, stdlib `sqlite3`, SQLite B-tree indexes and optional FTS5, FastMCP stdio. No new dependencies and no database migration.

---

## 1. Contract and behavior

### 1.1 Existing behavior remains authoritative

- A complete exact or normalized tag wins and must not be split.
- A complete high-confidence contextual resolution wins and must not be split.
- Existing response keys (`query`, `tag_library`, `entities`) remain present.
- Existing `results` and `suggestions` semantics remain unchanged for single-tag queries.
- Alias/retired/deleted filtering continues to use the existing resolver rules.

### 1.2 New multi-tag response

When decomposition succeeds, preserve the original query and return:

```json
{
  "query": "blushing red face",
  "tag_library": {
    "results": [],
    "suggestions": [],
    "query_mode": "multi_tag",
    "query_parts": [
      {
        "query": "blushing",
        "results": ["<normal single-tag result objects>"],
        "suggestions": []
      },
      {
        "query": "red face",
        "results": ["<normal single-tag result objects>"],
        "suggestions": []
      }
    ],
    "recommendation": {
      "action": "search_each_tag_separately",
      "original_query": "blushing red face",
      "queries": ["blushing", "red face"],
      "message": "This looks like multiple tags in one query. Search each recommended tag separately and combine the results for better recall."
    }
  },
  "query_recommendation": {
    "action": "search_each_tag_separately",
    "original_query": "blushing red face",
    "queries": ["blushing", "red face"],
    "message": "This looks like multiple tags in one query. Search each recommended tag separately and combine the results for better recall."
  },
  "entities": {}
}
```

The implementation may leave the normal entity lookup intact, but the new query recommendation must be top-level and machine-readable so an agent can immediately issue one search per item in `queries`.

### 1.3 Required examples

| Input | Required behavior |
|---|---|
| `blushing red face` | Split into `blushing` and `red face`; recommend two separate searches. |
| `blushing, red face` | Split on the explicit separator; recommend two separate searches. |
| `red face` | Keep as one known normalized tag (`red_face`); no `multi_tag` mode. |
| `closed mouth` | Keep as one known normalized tag (`closed_mouth`); no `multi_tag` mode. |
| `Fuwawa Hololive` | Preserve the high-confidence contextual character recommendation (`fuwawa_abyssgard` / `hololive_advent`); do not split. |
| `Mococo Hololive` | Preserve the high-confidence contextual character recommendation (`mococo_abyssgard` / `hololive_advent`); do not split. |
| `flash red face` | If both independent known tags cover the full input, return separate parts; preserve each tag's category. |
| one unknown word | Use the existing single-query fuzzy behavior; never create `multi_tag`. |

## 2. Decomposition rules

### 2.1 Precedence

1. Run the existing complete-query tag search.
2. If it returns results, return the existing single-query response.
3. If it returns no results, compute the existing complete-query suggestions.
4. Preserve the complete query if it contains a high-confidence `exact`, `normalized`, or `contextual` suggestion. This protects contextual character/franchise lookups.
5. Otherwise attempt deterministic decomposition.
6. If decomposition fails, return the existing suggestions unchanged.

Explicit separators (comma, semicolon, pipe, plus sign, or newline) override the contextual-preservation rule only when every resulting part is a known tag phrase.

### 2.2 Known phrase matching

- Normalize candidate phrases using the existing `_normalize_tag` helper.
- Resolve candidates through indexed exact tag lookup, not fuzzy matching.
- Accept existing canonical tag rows and valid active aliases according to the current database rules.
- Do not invent a phrase from arbitrary words.
- Do not use a full-table fuzzy scan to discover segments.

### 2.3 Space-only segmentation

For a query without an explicit separator:

- Tokenize Unicode words while retaining the original human-readable part text.
- Limit parsing to a bounded number of words (current prototype: 2–12 words) and a bounded phrase width (current prototype: up to 5 words).
- Build a dynamic-programming segmentation that covers every token with known tag phrases.
- Prefer the fewest parts, then prefer longer known phrases. This makes `red face` one phrase rather than `red` + `face`.
- Return only when at least two known parts cover the complete input.

### 2.4 Part resolution

Each part must be passed through the normal `_tag_rows` resolver independently. The part object uses ordinary result objects, including `name`, `category`, `post_count`, `match_type`, and `confidence`. Do not run fuzzy matching for a part that already has an exact or normalized result.

## 5. Risks and trade-offs

- **False splitting:** mitigated by complete-query precedence, high-confidence contextual preservation, exact indexed phrase matching, bounded DP, and full-input coverage.
- **Legitimate unknown multi-word tags:** they remain single-query fuzzy searches unless their phrase is present in the known tag dictionary.
- **Aliases:** a stored alias may be returned as its own exact part unless an existing canonical relation maps it; canonical alias cleanup is a separate data-quality task.
- **Performance:** the decomposition performs bounded B-tree exact checks only after the normal query path fails. Avoid unbounded candidate scans and avoid fuzzy searches for recognized parts.
- **Response compatibility:** new keys are additive. Consumers that only read `tag_library.results` still receive an empty list and can inspect `query_recommendation` for the actionable follow-up.
- **Agent compliance:** the server cannot force a model to make follow-up calls; the structured `action` and `queries` fields make the recommendation explicit and executable.
